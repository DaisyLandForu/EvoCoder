# Bear Code 架构设计

本文档用于从系统架构角度理解 Bear Code。它重点回答四个问题：

- Bear Code 为什么定位为自进化 Harness Agent？
- 一次用户请求在系统中如何流转？
- 各个核心模块之间的边界是什么？
- Skills、Memory、MCP、子 Agent 和工具系统如何被同一个 Runtime 编排？

如果你是第一次学习这个项目，建议先读 `README.md` 和 `wiki/从0到1学习了解项目.md`，再读本文档。本文档更偏工程架构，不会只介绍功能，而是解释模块为什么这样拆、数据为什么这样流动、哪些地方体现了 Harness Agent 的设计。

## 1. 总体定位

Bear Code 是一个本地运行的自进化 Harness Agent。这里的重点不是“模型能聊天”，而是“Runtime 能安全、稳定、可扩展地驱动模型完成真实软件工程任务”。

普通命令行聊天工具通常只有：

```text
用户输入
  -> 调用模型
  -> 打印模型回复
```

Bear Code 的结构更接近：

```text
用户输入
  -> CLI / REPL
  -> Agentic Harness（打开 run_start）
  -> 动态 Prompt / Memory / Skills / MCP 初始化
  -> 模型推理
  -> tool call
  -> ToolCallScheduler 切段
  -> PolicyEngine 授权
  -> 工具执行（共享 BudgetTracker）
  -> tool result 回写
  -> 多轮循环
  -> drain Skill 后台任务与 Memory 预取
  -> run_finished 后保存 Session
  -> 在线抽取只写 Candidate
```

所以 Bear Code 的核心不是单个工具，而是 Harness：

- 模型负责推理和提出工具调用意图。
- Harness 负责解释意图、检查策略、调度工具、记账预算、写 Trace、回写结果。
- Memory 和 Skills 负责长期上下文。
- MCP 和子 Agent 负责扩展能力边界。
- 自进化链路负责把用户反馈沉淀成可评测的 Candidate，而不是直接改 Active。

## 2. 总体架构图

![Bear Code 总体架构](assets/architecture/01-overall-architecture.svg)

从图上可以把系统分为六层：

| 层级 | 主要文件 | 职责 |
|------|----------|------|
| 入口层 | `agents/main.py`、`agents/ui.py` | 参数解析、REPL、一次性任务、命令处理、终端输出 |
| 配置层 | `agents/runtime_config.py` | RuntimeConfig、共享 BudgetTracker、子 Agent / Skill fork 降权 |
| Harness 层 | `agents/agent.py`、`agents/tool_scheduler.py`、`agents/trace.py` | Agent Loop、协议适配、工具切段调度、Trace 生命周期、会话保存 |
| 策略层 | `agents/policy.py`、`agents/plan_mode.py` | 路径边界、deny/allow、Plan Mode 状态机、MCP 信任、确认矩阵 |
| 能力层 | `agents/tools.py`、`agents/skills.py`、`agents/memory.py`、`agents/mcp_client.py`、`agents/subagent.py` | 文件工具、Shell、Skills、Memory、MCP、子 Agent |
| Prompt 层 | `agents/prompt.py` | 动态构建系统提示词；`memory_enabled=false` 时不注入 Memory Index |
| 演化层 | `agents/online_skill_evolution.py`、`agents/skill_registry.py`、`agents/skill_shadow_eval.py`、`agents/skill_gate.py` | 在线抽取 Candidate、三臂评测、Gate、promote / rollback |
| 评测层 | `benchmarks/`、`tests/` | 冻结配置的可复现 runner 与 CI |
| 持久化层 | `.bear/`、`~/.bear/`、`~/.BearCode/`、`~/.bear-code/`、`runs/` | Skills、Candidate/Champion、Trace、Memory、Session、Benchmark 产物 |

这个分层的好处是：模型协议、工具实现、长期记忆和自进化逻辑不会互相纠缠。`agent.py` 是调度中心，但具体能力分散在独立模块里。

## 3. 一次请求的主链路

![Bear Code Agent Loop 主链路](assets/architecture/02-chat-flow.svg)

主链路从 `agents/main.py` 进入，最终落到 `Agent.chat()`。

```text
用户输入
  -> run_repl() 或 run_one_shot()
  -> Agent.chat(user_message)
  -> 打开 run_start（新 run_id）
  -> 首次 chat 初始化 MCP（仓库级配置需用户目录信任）
  -> 取出上一轮 pending skill extraction window
  -> 检索 Skills 并注入用户消息
  -> 根据协议选择 _chat_openai() 或 _chat_anthropic()
  -> 模型返回文本或工具调用
  -> ToolCallScheduler：连续只读可并发，副作用是屏障
  -> PolicyEngine.authorize()
  -> 工具执行；子 Agent 共享 BudgetTracker
  -> tool result 回写模型
  -> 模型继续推理或结束
  -> 后台执行 Skill usage tracking / online evolution（只写 Candidate）
  -> drain 后台任务与 Memory 预取
  -> run_finished（本 run 增量）后 unbind Trace
  -> 保存新的 pending window
  -> 自动保存 Session
```

这条链路里有四个关键点：

1. **模型不直接执行动作**  
   模型只能返回 tool call，真正执行动作的是 Harness。

2. **工具执行前有硬策略边界**  
   路径逃逸、deny、Plan Mode、MCP 信任不能被项目 `allow` 规则抬升。

3. **任务结束后才做能力沉淀，且不改 Active**  
   下一轮用户反馈到来后，在线抽取只写入 Candidate。

4. **一次对话是一棵 Trace**  
   Skill 后台任务和 Memory 预取必须在 `run_finished` 前结束；REPL 治理命令另开 run。

## 4. 入口层设计

入口层主要在 `agents/main.py`。

它承担的职责包括：

- 解析 CLI 参数。
- 加载 `.env`。
- 判断模型协议。
- 创建 `Agent` 实例。
- 启动 REPL 或一次性任务。
- 处理 REPL 内置命令。
- 将用户确认函数注入 Agent。

关键入口：

| 函数 | 作用 |
|------|------|
| `parse_args()` | 解析 `--model`、`--api-base`、`--resume`、`--plan`、权限模式等参数 |
| `_load_env_file()` | 从当前目录或父目录加载 `.env` |
| `_resolve_api_config()` | 判断使用 OpenAI-compatible 还是 Anthropic-compatible |
| `run_repl()` | 交互式 REPL 主循环 |
| `run_one_shot()` | 执行一次性任务 |
| `main()` | 程序总入口 |

入口层不直接关心工具怎么执行，也不关心 Skills 怎么演化。它只负责把用户输入和配置转成 Agent 可以消费的运行参数。

## 5. Harness 层设计

Harness 层集中在 `agents/agent.py`，这是项目最核心的文件。

`Agent` 内部维护了这些状态：

| 状态 | 含义 |
|------|------|
| `config` | `RuntimeConfig`：workspace、权限、超时、预算、trace、memory/folding 开关 |
| `permission_mode` | 当前权限模式，来自 RuntimeConfig |
| `model` | 当前模型名，来自 CLI 或 `.env` 的 `MODEL` |
| `use_openai` | 是否走 OpenAI-compatible 路径 |
| `tools` | 当前可用工具列表，包含内置工具和 MCP 动态工具 |
| `_anthropic_messages` / `_openai_messages` | 两套协议各自的消息历史 |
| `_mcp_manager` | MCP Server 管理器 |
| `_tracer` / `_run_id` | 本轮根 run 的 Trace 绑定 |
| `_last_retrieved_skill_reference` | 本轮检索到的 Skill 参考，用于后续 usage judge |
| `_pending_skill_extraction_window` | 等待下一轮反馈验证的 Skill 沉淀窗口 |
| `_background_skill_tasks` | 后台 Skill usage / evolution 任务 |

`Agent.chat()` 是最重要的运行时入口。它本身不负责所有细节，而是把任务拆给多个内部方法：

| 方法 | 职责 |
|------|------|
| `_open_root_run()` / `_close_root_run()` | 打开/关闭根 Trace；`run_finished` 写本 run 增量 |
| `_traced_operation()` | 给 REPL `/skill-eval` `/compact` `/extract_now` 独立 run |
| `_augment_user_message_with_skill_context()` | 检索相关 Skills 并把上下文注入用户消息 |
| `_chat_openai()` | OpenAI-compatible 模型循环 |
| `_chat_anthropic()` | Anthropic-compatible 模型循环 |
| `_execute_tool_call()` | 统一分发工具调用 |
| `_execute_skill_tool()` | 执行 Skill 工具，支持 inline / fork |
| `_execute_agent_tool()` | 启动子 Agent；子配置权限只能降 |
| `_run_online_skill_evolution()` | 后台执行在线 Skill 抽取，落点 Candidate |
| `_run_skill_usage_tracking()` | 判断检索到的 Skill 是否真的有用 |
| `_settle_memory_prefetch_tasks()` | 在 run 结束前收口 Memory 预取 |
| `_auto_save()` | 自动保存会话 |
| `_run_compression_pipeline()` | 控制长上下文和大工具结果 |

这个设计体现了 Harness Agent 的核心：模型协议、工具路由、权限、安全、长期上下文和自进化都在同一个 Runtime 中协调。

## 6. 模型协议适配

Bear Code 支持两类模型协议：

- OpenAI-compatible
- Anthropic-compatible

协议判断主要在 `agents/main.py::_resolve_api_config()`。

运行时分支在 `Agent` 中：

```text
self.use_openai = bool(api_base)

if self.use_openai:
    self._chat_openai(user_message)
else:
    self._chat_anthropic(user_message)
```

两条路径的差异主要体现在：

| 差异点 | OpenAI-compatible | Anthropic-compatible |
|--------|-------------------|----------------------|
| 客户端 | `openai.AsyncOpenAI` | `anthropic.AsyncAnthropic` |
| 消息容器 | `_openai_messages` | `_anthropic_messages` |
| 工具定义格式 | OpenAI tools schema | Anthropic tools schema |
| tool call 表达 | `tool_calls` | `tool_use` block |
| tool result 回写 | `tool` role message | `tool_result` block |

但它们共享：

- Skills 检索。
- Memory 预取（可被 `memory_enabled` 关闭）。
- MCP 初始化。
- PolicyEngine 与 ToolCallScheduler。
- 共享 BudgetTracker（未知 usage 成本为 `null`）。
- Session 保存。
- 上下文压缩。
- Online Skill evolution（只写 Candidate）。

这就是协议适配层的边界：底层消息格式可以不同，但上层能力体系尽量统一。

## 7. 工具系统与权限架构

![工具与权限流程](assets/architecture/09-tool-permission-flow.svg)

工具系统主要在 `agents/tools.py`，策略边界在 `agents/policy.py`，调度在 `agents/tool_scheduler.py`，Plan Mode 状态机在 `agents/plan_mode.py`。

工具定义集中在 `tool_definitions`，包括：

- `read_file`
- `write_file`
- `edit_file`
- `list_files`
- `grep_search`
- `shell`
- `skill`
- `create_skill`
- `evolve_skill`
- `skill_feedback`
- `skill_stats`
- `agent`
- Plan Mode 相关工具

执行链路是：

```text
模型发起 tool call
  -> ToolCallScheduler 按模型顺序切段
  -> 连续只读（read_file / list_files / grep_search）可并发
  -> 写文件、Shell、agent、skill 是屏障
  -> PolicyEngine.authorize()
  -> 特殊工具由 Agent 层路由，其余进入 tools.execute_tool()
  -> 结果截断或格式化
  -> tool result 回写模型
```

`PolicyEngine.authorize()` 的判定顺序是硬编码的：

```text
父策略 deny
  -> 路径 / symlink 逃逸
  -> settings deny 规则
  -> Plan Mode 硬边界
  -> MCP 信任硬边界
  -> settings allow 规则（只能去掉确认，不能抬升硬边界）
  -> bypassPermissions
  -> 只读 / 控制工具放行
  -> 确认矩阵
```

Plan Mode 是独立状态机：`DEFAULT → PLANNING → AWAITING_APPROVAL → EXECUTING → DEFAULT`。审批函数 `await` 计划正文，而不是只看文件是否存在。子 Agent / Skill fork 通过 `RuntimeConfig.derive_child()` 继承预算，权限只能降不能升。

## 8. Skills 架构

![Skills 概念流程](assets/architecture/10-skills-concept-flow.svg)

Skills 是 Bear Code 的长期能力沉淀方式。它不是 Memory，也不是系统提示词硬编码，而是磁盘上的 `SKILL.md`。

Skill 的职责是保存“可复用方法”，例如：

- 固定代码审查流程。
- 某类文档写作风格。
- 某个项目的发布检查清单。
- 某类重构任务的步骤。
- 某个领域任务的输出结构。

相关模块：

| 文件 | 职责 |
|------|------|
| `agents/skills.py` | 加载、解析、检索、执行 Skill |
| `agents/online_skill_evolution.py` | 在线抽取；add / merge 调用 `create_candidate()` |
| `agents/skill_registry.py` | Candidate / Champion / Active 隔离、promote / rollback |
| `agents/skill_shadow_eval.py` | 三臂成对 Shadow 评测 |
| `agents/skill_gate.py` | NTR / 收益 / 成本 Gate |
| `agents/skill_evolution.py` | 手工 `/skill-create` `/skill-evolve` 写 Active，以及旧审计 |
| `.bear/skills/` | 项目级 Active Skills |
| `.bear/skill-evolution/candidates/` | 在线反馈的唯一落点 |
| `~/.bear/skills/` | 用户级 Skills |

运行时分为三段：

```text
对话前
  -> discover_skills()
  -> retrieve_relevant_skills()
  -> format_retrieved_skill_context()
  -> 注入用户消息

对话中
  -> 模型可以调用 skill 工具
  -> inline 模式返回 Skill prompt
  -> fork 模式创建子 Agent 执行 Skill（权限只能降）

对话后
  -> judge_retrieved_skill_usage()
  -> online_ingest()
  -> add / merge 写入 Candidate，不改 Active
```

Skills 的关键设计是：检索、执行、演化、评测、激活分离。这样可以避免 Skill 被模型在没有证据和 Gate 的情况下改写线上能力。

## 9. Skills 自进化架构

![Skills 自进化总体链路](assets/architecture/07-skills-evolution-flow.svg)

Skills 自进化是 Bear Code 最核心的差异点之一。

它的目标不是让 Agent 随机改 prompt，而是把用户明确反馈中稳定、可复用、未来仍有价值的方法沉淀为 **Candidate**，再经过评测才能进入 Active。

自进化链路分为六步：

1. **当前轮完成任务**  
   Agent 正常回答用户，并记录当前输入、输出和检索到的 Skill。

2. **等待下一轮反馈**  
   下一轮用户输入可能包含“以后都这样”“刚才那种格式不错”“不要再这么写”等反馈。

3. **Extractor 抽取候选**  
   `online_skill_evolution.py` 使用模型判断反馈是否能形成可复用 Skill 候选。

4. **Maintainer 决策维护**  
   Maintainer 结合现有 Skills 和相似检索结果，决定 add、merge 或 discard。add / merge 只写 `.bear/skill-evolution/candidates/`。

5. **Shadow 评测与 Gate**  
   同一次运行重新生成 `no_skill` / `current_champion` / `candidate`。Gate 看 NTR、成对收益、成本增幅、硬失败、Holdout、独立 Judge。不满足则为 `incubating`。

6. **显式激活与回滚**  
   通过 Gate 后 `mark_champion`，Active 仍需 `/skill-promote`。激活前快照旧 Active；需要时 `/skill-rollback`。

`/skill-create` 与 `/skill-evolve` 仍直接写 Active，属于用户显式手工命令，不属于自动反馈链路。

落盘目录：

| 路径 | 说明 |
|------|------|
| `candidates/<skill>/<version>/` | 用户反馈的唯一落点 |
| `champions/<skill>/` | 通过 Gate 的版本 |
| `snapshots/` | 每次激活前的 Active 快照 |
| `evaluations/` | 评测产物（含阈值与配置） |
| `holdout/` | 与候选生成无关的独立样本 |
| `registry.json` | 版本、状态、来源与迁移历史 |

这种设计让“自进化”具备可控性：

- 有用户反馈作为证据。
- 有 add / merge / discard 决策。
- Candidate 与 Active 物理隔离。
- 有三臂成对评测和 NTR Gate。
- 有原子激活和回滚快照。

## 10. Memory 架构

![Memory 召回流程](assets/architecture/12-memory-recall-flow.svg)

Memory 和 Skills 的职责不同：

| 类型 | 保存内容 | 示例 |
|------|----------|------|
| Memory | 事实、偏好、背景、历史决策 | 用户喜欢中文回答；项目部署在 Docker；某接口已经废弃 |
| Skills | 方法、流程、风格、可复用操作步骤 | 代码审查按安全、性能、可维护性三段输出 |

Memory 模块在 `agents/memory.py`。

核心流程：

```text
保存 Memory
  -> save_memory()
  -> 写入 ~/.BearCode/projects/<project_hash>/memory/
  -> 更新 index.md

召回 Memory
  -> scan_memory_headers()
  -> start_memory_prefetch()
  -> select_relevant_memories()
  -> format_memories_for_injection()
  -> 注入模型上下文
```

Memory 使用项目路径 hash 隔离，避免不同项目之间的长期记忆互相污染。

## 11. MCP 架构

![MCP 概念流程](assets/architecture/11-mcp-concept-flow.svg)

MCP 是 Model Context Protocol，用来让外部工具以统一协议暴露给 Agent。Bear Code 不依赖 MCP SDK，而是自己实现 stdio JSON-RPC Client。

相关模块是 `agents/mcp_client.py`。

内部有两个核心对象：

| 对象 | 职责 |
|------|------|
| `McpConnection` | 管理一个 MCP Server 子进程，发送 JSON-RPC 请求，读取响应 |
| `McpManager` | 读取配置，启动多个 Server，合并工具定义，路由工具调用 |

MCP 启动流程：

```text
Agent.chat() 首次执行
  -> 检查仓库级 MCP 配置是否已信任
  -> 信任记录：~/.bear/mcp-trust/<workspace_id>.json
  -> McpManager.load_and_connect()
  -> 读取全局 / 用户 / 项目 MCP 配置
  -> 启动 MCP Server 子进程
  -> initialize
  -> tools/list
  -> 包装为 mcp__server__tool
  -> 合并进 Agent.tools
```

调用流程：

```text
模型调用 mcp__server__tool
  -> Agent._execute_tool_call()
  -> McpManager.is_mcp_tool()
  -> McpManager.call_tool()
  -> McpConnection.call_tool()
  -> JSON-RPC tools/call
  -> 返回结果给模型
```

MCP 的架构意义是：Bear Code 不需要把所有外部能力都内置，只要外部工具能以 MCP Server 形式暴露，就能进入同一套 Harness。仓库级配置的信任记录必须写在用户目录，不能进仓库，否则 clone 下来会变成预信任。

## 12. 子 Agent 架构

子 Agent 用来处理独立探索、规划或局部任务，避免所有上下文都堆在主 Agent 中。

相关模块：

| 文件 | 职责 |
|------|------|
| `agents/subagent.py` | 定义内置子 Agent，发现自定义子 Agent |
| `agents/agent.py` | 通过 `_execute_agent_tool()` 创建并运行子 Agent |

子 Agent 执行流程：

```text
模型调用 agent 工具
  -> Agent._execute_agent_tool()
  -> get_sub_agent_config(agent_type)
  -> RuntimeConfig.derive_child()：共享 BudgetTracker，权限只能降
  -> 子 Agent 挂到 subagent_started.step_id
  -> 子 Agent 独立 run_once()
  -> 精简结果返回主 Agent
```

子 Agent 的关键价值：

- 隔离上下文。
- 降低主 Agent 消息历史膨胀。
- 让探索、计划、通用任务可以使用不同 prompt。
- 支持项目级和用户级自定义 Agent。
- 与父 Agent 共享预算；未知 usage 同样记为 `null`。

Skill 的 `fork` 模式也使用类似思路：把 Skill prompt 作为子 Agent 的 system prompt，让某个能力在隔离上下文中执行。

## 13. Prompt 架构

Prompt 构建在 `agents/prompt.py`。

`build_system_prompt()` 不是简单返回固定文本，而是动态拼接：

- 基础身份和工作规则。
- 当前目录。
- Git 上下文。
- 项目规则文件。
- Memory System 说明和 Memory Index。
- Available Skills。
- Available Sub Agents。

动态 Prompt 的价值是：Runtime 状态变化后，模型能看到最新能力。

例如：

- 新增 Skill 后，Skills 列表会更新。
- 新增自定义子 Agent 后，Agent 描述会更新。
- 新增 Memory 后，Memory Index 会更新。
- 项目规则变化后，Prompt 会重新加载。

这也是为什么 `Agent._refresh_runtime_system_prompt()` 很重要：当 Memory、Skills、Agent 配置变化后，系统提示词需要重新构建。

## 14. 会话、压缩与大结果持久化

长任务会产生大量消息和工具结果。如果不处理，模型上下文会快速膨胀。

相关模块：

| 文件 | 职责 |
|------|------|
| `agents/session.py` | 保存、加载、列出 session |
| `agents/agent.py` | 自动保存、恢复、压缩消息、大结果持久化 |

主要机制：

| 机制 | 说明 |
|------|------|
| `_auto_save()` | 每轮结束后保存 session |
| `restore_session()` | `--resume` 时恢复会话 |
| `_check_and_compact()` | 检查上下文是否需要压缩 |
| `_compact_conversation()` | 触发模型总结历史上下文 |
| `_run_compression_pipeline()` | 对消息和工具结果做多级压缩 |
| `_persist_large_result()` | 大工具结果写入文件，只把引用留在上下文中 |

这部分保证 Bear Code 不只是能完成一轮任务，而是能支撑多轮长任务。

## 15. 数据与存储架构

![数据与存储架构](assets/architecture/04-data-storage.svg)

重要路径如下：

| 数据 | 路径 | 说明 |
|------|------|------|
| 项目级 Active Skills | `.bear/skills/<skill_name>/SKILL.md` | 只能由 promote / rollback 或手工命令写入 |
| 用户级 Skills | `~/.bear/skills/<skill_name>/SKILL.md` | 跨项目复用能力 |
| Candidate / Champion / 评测 | `.bear/skill-evolution/` | 在线反馈、Gate 产物、快照、registry |
| Trace | `.bear/traces/<run_id>.jsonl` | 事件级轨迹 |
| MCP 信任 | `~/.bear/mcp-trust/<workspace_id>.json` | 仓库级 MCP 配置的用户信任记录 |
| Memory | `~/.BearCode/projects/<project_hash>/memory/` | 项目隔离的长期记忆 |
| Session | `~/.bear-code/sessions/` | 会话恢复数据 |
| 大工具结果 | `~/.bear-code/tool-results/` | 大输出持久化引用 |
| Plan 文件 | `~/.bear/plans/` | Plan Mode 生成的计划 |
| MCP 配置 | `.mcp.json`、settings | 外部工具 Server 配置 |
| Benchmark 产物 | `runs/<run_id>/` | 冻结配置、逐题结果、Trace、summary |

存储设计体现了三个原则：

- 项目相关能力放项目目录，便于随项目沉淀。
- 用户级偏好、MCP 信任和跨项目能力放 home 目录，便于复用且避免预信任。
- Active 与 Candidate 分目录，反馈改不到线上。

## 15.5 Trace、预算与可复现评测

Trace 在 `agents/trace.py`。每次根 `chat()` 生成新 `run_id`；子 Agent 挂到 `subagent_started.step_id`。`run_finished` 写本 run 增量，`session_*` 写会话累计。未知 usage 成本为 `null`；设置了 `max_cost` 则保守停止。Side Query 调用前也检查预算。REPL `/skill-eval`、`/compact`、`/extract_now` 走 `_traced_operation`，独立 run，结束后清空 Recorder。

可复现评测入口是 `python -m benchmarks.runner`。冻结项包括 task_ids、task_digest（含 files）、tools、memory/folding、temperature、seed、git SHA。`memory_enabled=false` 时 System Prompt 不注入本机 Memory Index。历史 GAIA/HLE 分数没有对应 runner，标为未验证，细节见 `wiki/评测部分.md`。

CI：`.github/workflows/ci.yml` 跑 `ruff check agents tests benchmarks` 和 `pytest -q`，不依赖真实 API Key。

## 17. 为什么说它是自进化 Harness Agent

Bear Code 不是只把模型包成 CLI，也不是只提供几个文件工具。它的核心架构是：

```text
Agentic Harness
  -> 管模型协议
  -> 管工具调度
  -> 管策略边界
  -> 管共享预算
  -> 管 Trace
  -> 管上下文
  -> 管长期记忆
  -> 管 Skills 治理
  -> 管 MCP 信任
  -> 管子 Agent
  -> 管会话和压缩
  -> 管用户反馈到 Candidate 的沉淀
```

“自进化”体现在：

- 用户反馈会进入 pending window。
- Extractor 会判断是否能抽取可复用方法。
- Maintainer 会判断 add、merge 或 discard。
- 在线落点是 Candidate，不是 Active。
- Gate 用三臂重跑和 NTR 决定能否成为 Champion。
- Active 只由显式 promote / rollback 改写。

“Harness Agent”体现在：

- 模型不直接操作环境。
- 所有动作经过 Runtime。
- 工具、策略、预算、Trace、长期上下文和外部能力由 Runtime 统一编排。
- 同一套机制可以接不同模型、不同工具和不同子 Agent。

所以 Bear Code 的架构价值不只是“能写代码”，而是构建了一套可运行、可扩展、可审计、可复现评测、可持续沉淀能力的 Agent Runtime。
