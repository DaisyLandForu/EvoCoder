# Bear Code 技术亮点

本文档梳理 Bear Code 的技术亮点。重点不是罗列 CLI 功能，而是说明 Bear Code 作为一个自研 Agentic Harness，如何把模型推理、工具调用、权限控制、会话记忆折叠、Skills 自进化、MCP、子 Agent 和评测链路组织成一个可运行、可沉淀、可审计的 Coding Agent Runtime。

## 1. 项目定位

Bear Code 是一个本地命令行 Coding Agent Runtime。它的核心不是“套一层大模型 API”，而是实现了一套 Harness：

```text
用户输入
  -> 构建 system prompt、Memory、Skills、MCP 工具上下文
  -> 调用 OpenAI / Anthropic 兼容模型
  -> 解析 tool call
  -> PolicyEngine 授权、ToolCallScheduler 调度
  -> 执行内置工具 / Skills / MCP 工具 / 子 Agent
  -> 工具结果回写模型
  -> 必要时折叠会话记忆
  -> drain 后台任务，关闭 Trace run
  -> 保存 session；在线抽取只写 Candidate
```

因此，项目亮点集中在三个层面：

- **运行时编排**：统一管理模型、工具、策略、调度、预算、Trace 和持久化。
- **长程任务能力**：通过自主会话记忆折叠和分层 Memory / Skills，降低上下文膨胀对任务推进的影响。
- **自进化能力**：把用户后续反馈沉淀为 Candidate，经三臂 Shadow 评测和 Gate 后才能成为 Champion；Active 只由显式 promote / rollback 改写。
- **可复现评测**：事件级 Trace + `benchmarks/` 冻结配置；历史 GAIA/HLE 分数不可由本仓库复现。

## 3. Agentic Harness 运行时

### 解决的问题

普通聊天式工具只完成“用户输入 -> 模型回复”。但 Coding Agent 需要持续处理模型请求、工具调用、权限判断、工具结果、上下文压缩、会话保存和后台沉淀。Bear Code 将这些能力收敛到 `Agent` 运行时中，形成完整的推理、行动、观察、继续推理闭环。

### 实现思路

核心入口是 `Agent.chat()`：

```text
打开 run_start（新 run_id）
  -> 初始化 MCP（仓库级配置需用户目录信任记录）
  -> 弹出上一轮 pending window
  -> 检索并注入相关 Skills
  -> 根据协议进入 OpenAI 或 Anthropic 主循环
  -> 模型产生 tool call
  -> ToolCallScheduler 切段，PolicyEngine 授权
  -> 收集 assistant 输出
  -> 后台触发 Skills usage tracking 和 online evolution（只写 Candidate）
  -> drain 后台任务与 Memory 预取
  -> run_finished（本 run 增量）后 unbind Trace
  -> 保存 session
```

工具调用统一从 `_execute_tool_call()` 分发：

- `compact_context`：触发自主会话记忆折叠。
- `skill`：调用已注册 Skill，支持 inline 和 fork。
- `agent`：启动子 Agent。
- `mcp__server__tool`：路由到 MCP server。
- 其他工具：交给 `agents/tools.py` 执行。

### 技术价值

- **统一控制权**：模型只提出 tool call，本地动作由 Runtime 执行。
- **协议可替换**：OpenAI-compatible 与 Anthropic-compatible 复用同一套工具、Memory、Skills 和权限体系。
- **能力可扩展**：内置工具、MCP 工具、Skills、子 Agent 都能纳入统一调度。
- **状态可保存**：每轮结束自动保存 session，并为后续自进化提供对话证据。

## 4. 自主会话记忆折叠

### 解决的问题

长程任务中，原始对话、工具结果、失败尝试和中间分析会持续堆积，导致上下文变长、关键信息被淹没、失败路径影响后续推理。Bear Code 借鉴 DeepAgent 的 memory folding 思路，将它实现为“自主会话记忆折叠”：它不是简单裁剪历史，而是把会话重组为可继续执行的结构化状态。

### 实现思路

折叠 schema 在 `agents/session_memory.py` 中定义，包含三层：

```text
episode_memory
  -> 任务描述、关键事件、当前进度

working_memory
  -> 当前子目标、阻塞点、下一步动作

tool_memory
  -> 已用工具、有效参数、常见错误、返回模式、工具经验
```

触发方式有两类：

- **模型主动触发**：模型可以调用 `compact_context` 工具，适用于上下文变长、工具反复失败、策略需要重启等场景。
- **系统阈值兜底**：当输入 token 接近上下文阈值时，Runtime 自动调用折叠流程。

折叠流程大致为：

```text
收集当前会话 transcript
  -> 调用 side query 生成三层结构化 JSON
  -> 解析失败时使用 fallback folded memory
  -> 将原始历史替换为 <session-folded-memory>
  -> 折叠记录落盘到 .bear/sessions/
  -> Agent 从折叠后的状态继续执行
```

### 代码落点

- `agents/session_memory.py`：定义三层 session memory schema、transcript 构造、JSON 解析和 fallback。
- `agents/tools.py`：暴露 `compact_context` 工具。
- `agents/agent.py`：实现 `_compact_conversation()`、`_execute_compact_context_tool()`、自动阈值触发和折叠后消息重建。
- `agents/session.py`：将折叠记录保存到当前项目 `.bear/sessions/`。

### 技术价值

自主会话记忆折叠的价值不只是减少 token，而是支持长程任务中的状态重组：

- 保留任务进度、当前子目标、阻塞点和下一步动作。
- 保留工具调用经验，避免重复走失败路径。
- 在策略变化或多次失败后，为 Agent 提供“重新整理局面”的机会。
- 让长对话不依赖完整原始历史，也能从结构化状态继续推进。

需要注意的是，当前 `--resume` 主要恢复原始模型消息历史；折叠记录会作为审计和最新折叠状态保存到 `.bear/sessions/`，不是一个独立的跨进程长期记忆系统。

## 5. Memory + Skills 分层长期上下文

### 解决的问题

Agent 需要记住两类不同信息：

- **Memory**：项目事实、用户偏好、历史决策、参考资料。
- **Skills**：可复用的方法、工作流、格式要求和任务策略。

如果把它们混在同一段 prompt 中，会导致上下文污染：项目事实可能被当成通用方法，任务流程也可能被误认为当前项目状态。

### 实现思路

Bear Code 将 Memory 和 Skills 分层：

- `agents/memory.py` 负责文件型长期记忆。它按当前项目隔离 memory 目录，使用 Markdown + frontmatter 保存条目，并通过 side query 选择相关 memory 注入当前会话。
- `agents/skills.py` 负责 Skills 加载、检索和调用。它扫描用户级 `~/.bear/skills/` 和项目级 `.bear/skills/`，解析 `SKILL.md`，并使用 BM25-lite 检索相关 Skills。

Skills 支持两种执行模式：

- **inline**：将 Skill 指令注入当前上下文，由主 Agent 继续执行。
- **fork**：启动隔离子 Agent 执行 Skill，适合需要独立上下文的任务。

### 技术价值

- Memory 解决“这件事之前发生过什么”。
- Skills 解决“这类事以后应该怎么做”。
- 两者分层后，长期上下文更可控，也更适合长程任务和重复任务。

## 6. Skills 自进化

### 解决的问题

很多用户反馈不是一次性的，例如“以后写简历不要写成 STAR 标题”“评测文档只保留 Pass@1”“这类内容要先给结论”。如果这些反馈只留在当前会话里，下次仍然需要用户重复说明。

Bear Code 的 Skills 自进化链路就是把稳定反馈沉淀为 Candidate；只有 Gate 通过并由用户 promote 后，才进入 Active `SKILL.md`。

### 实现思路

自进化流程以 pending window 为核心：

```text
本轮用户请求 + assistant 回复
  -> 保存 pending window
下一轮用户输入
  -> 作为上一轮反馈证据合并进 window
  -> Extractor 抽取最多一个可复用 Skill 候选
  -> Maintainer 结合已有 Skills 做相似检索
  -> 决策 add / merge / discard
  -> add / merge 写入 `.bear/skill-evolution/candidates/`
  -> 记录 provenance；Active 保持不变
```

Extractor 的约束包括：

- 用户消息是主要证据，assistant 只能作为上下文。
- 只抽取可复用的工作流、输出策略、实现偏好或纠正。
- 不抽取一次性任务内容、隐私、URL、账号 ID、精确日期和临时参数。

Maintainer 的约束包括：

- 已有相同能力时优先 merge，不盲目新增。
- 重复且无增量价值时 discard。
- merge 时保留已有有用指导，只加入稳定新规则。

### 代码落点

- `agents/online_skill_evolution.py`：Extractor、Maintainer、online ingest；add/merge 调用 `create_candidate()`。
- `agents/skill_registry.py`：Candidate / Champion / Active 隔离、原子 promote、rollback 快照。
- `agents/agent.py`：在每轮对话后调度 usage tracking 和 online skill evolution，并在 `run_finished` 前 drain。

### 技术价值

- 把用户反馈从“当前上下文提醒”变成“可评测的候选能力”。
- 通过 add / merge / discard 控制 Skill 膨胀。
- 通过目录隔离保证反馈改不到线上 Active。

## 7. Skills 自进化质量评测

### 解决的问题

自动沉淀 Skill 之后，不能默认它就是正确的。需要回答几个问题：

- 这个 Skill 从哪些真实对话来？
- 它在历史任务中是否真的改善了输出？
- 规则是否可回放、可比较？
- 候选改进是否优于当前版本？
- 哪个版本可以作为当前本地已知的健康版本？

Bear Code 使用在线 Skills 评测链路对这些问题做质量观察。

### 实现思路

评测入口在 `agents/skill_shadow_eval.py`。核心流程：

```text
读取 Candidate / Champion
  -> 构造 replay + holdout（生成样本强制降为 replay）
  -> 从 Champion（或 Candidate）编译统一规则
  -> 同一次运行重新生成 no_skill / current_champion / candidate
  -> 独立 Judge 配置；同模型只能 incubating
  -> Gate：硬失败、成对收益、NTR、成本增幅
  -> 通过后 mark_champion，Active 仍需 /skill-promote
```

当前支持的评测能力包括：

- **三臂成对重跑**：同一次运行重新生成 `no_skill` / `current_champion` / `candidate`，禁止拿历史 `latest_assistant` 当 Champion 基线。
- **规则评测**：根据 Skill 文本编译非空、JSON、表格、引用来源等程序规则，三臂共用 `agents/skill_rules.py`。
- **独立 Judge**：Judge 与 Generator 同模型时只能 `incubating`。
- **Gate**：硬失败、成对收益、NTR、成本增幅、Holdout；不满足则 `incubating`。
- **原子激活**：通过 Gate 后 `mark_champion`，Active 仍需 `/skill-promote`；激活前快照旧 Active。

`/skill-create` 与 `/skill-evolve` 仍直接写 Active，属于用户显式手工命令，不是自动反馈链路。

### 边界说明

当前 champion 是本地评测记录和候选产物，不会自动覆盖 active `SKILL.md`。这能避免一次评测结果直接改写线上能力，更符合可审计、可回滚的自进化设计。

## 8. 工具系统、权限控制与 Plan Mode

### 解决的问题

Coding Agent 可以读写文件、执行 Shell、创建 Skill、调用外部工具。如果没有工具边界，风险包括：

- 未读文件就编辑，覆盖用户修改。
- 执行危险命令。
- 在计划阶段提前修改项目。
- 随意创建或演化 Skill，污染长期能力。

### 实现思路

`agents/tools.py` 将工具分为只读、编辑和需要确认的动作：

- 只读工具：`read_file`、`list_files`、`grep_search`、`compact_context`。
- 编辑工具：`write_file`、`edit_file`、`skill_create`、`skill_evolve`。
- Shell 工具：根据命令风险进入确认或拒绝路径。

关键保护包括：

- Plan Mode 下阻断普通写操作和 Shell，只允许围绕计划文件工作。
- 写入新文件、危险命令、Skill 创建和 Skill 演化需要确认。
- 编辑已有文件前必须先 `read_file`，并记录 mtime；如果文件在读取后被外部修改，需要重新读取。

### 技术价值

这部分体现的是 Harness 的控制边界：模型可以提出动作，但是否执行、如何执行、是否需要确认，都由 Runtime 决定。

## 9. MCP 与子 Agent

### MCP 外部工具接入

Bear Code 自己实现了 stdio JSON-RPC MCP Client，而不是把外部工具硬编码进项目。实现路径：

```text
读取 ~/.bear/settings.json、.bear/settings.json、.mcp.json
  -> 启动 MCP server 子进程
  -> initialize
  -> tools/list
  -> 包装为 mcp__server__tool
  -> 模型调用时路由到 tools/call
```

这样可以把浏览器、搜索、数据库、内部系统等外部能力统一接入 Agent 工具层。

### 子 Agent

子 Agent 用于隔离上下文和任务边界。当前内置：

| 类型 | 工具范围 | 适用场景 |
| --- | --- | --- |
| `explore` | 只读工具 | 快速代码搜索、定位实现 |
| `plan` | 只读工具 | 输出结构化实施计划 |
| `general` | 除 `agent` 外的大部分工具 | 独立处理局部任务 |

项目还支持 `.bear/agents/*.md` 自定义子 Agent，并可通过 `allowed-tools` 控制工具范围。

## 10. 长程任务测评结果

当前可复现评测入口是 `benchmarks/` 与 `runs/<run_id>/`。`wiki/评测部分.md` 中的 GAIA / HLE Pass@1（53.3 / 20.2 以及折叠消融 44.7）是 **历史未验证** 数字：仓库没有对应 runner、冻结配置或逐题 Trace，不能当作本仓库当前结果，也不能宣传多模态能力。

与 HiRA 的 42.1 / 13.6 对比同样无法由本仓库复现。

### 可复现指标

`python -m benchmarks.runner` 产出：

- Task Success Rate
- 平均 Tool Steps
- P95 Latency
- 平均 Token / 成本
- Hard Failure
- NTR 与三臂成对差值

每题都有 `results.jsonl` 行和 `traces/<task_id>.jsonl`。失败样本保留，不从结果集中剔除。`memory_enabled=false` 时不注入本机 Memory Index。未知 usage 的成本为 `null`。已有 `run_id` 会重建整棵产物目录。

## 12. 当前实现边界

为了保证表述和代码一致，当前文档对以下边界做明确说明：

- 自主会话记忆折叠是 session 级状态折叠，不等同于完整的跨项目长期记忆系统。
- 折叠产物会保存到项目 `.bear/sessions/`，当前 `--resume` 主要恢复模型消息历史，折叠记录更多承担审计和状态记录作用。
- champion 是评测产物和健康版本记录，不会自动覆盖当前 active Skill。
- `/skill-create` / `/skill-evolve` 是手工写 Active，不属于在线反馈链路。
- LLM judge 和三臂重跑依赖可用的模型 side query；没有该能力时，评测会退化为程序规则评测。
- 未知 usage 时成本为 `null`；设了 `max_cost` 则保守停止，不得把未知记成 0。
- GAIA / HLE 历史分数无法由当前仓库代码 + Trace 复现，对外只能引用 `benchmarks/` 产物。
- 当前 Runtime 没有多模态视觉工具，不宣传 MM 能力。
