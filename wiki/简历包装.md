## 2.5 自主会话记忆折叠：目的与价值

### 目的

面向代码探索、调试、重构和多工具协作等长程任务，避免原始对话、工具结果和失败尝试持续堆积，导致上下文膨胀、关键信息被淹没或错误路径持续影响后续推理。

### 核心收益

- **降低上下文开销**：将冗长交互历史压缩为结构化 session state，释放上下文空间。
- **保持任务连续性**：保留整体进展、当前子目标、阻塞问题、下一步动作和工具经验，折叠后可以继续执行。
- **减少错误累积**：在重复失败或策略变化时清理噪声，让 Agent 重新审视当前状态并调整方案。
- **提升长程任务稳定性**：相比固定截断或简单摘要，三层 memory schema 能更稳定地保留任务事实、工作状态和工具使用经验。

### 简历表述

> 设计自主会话记忆折叠机制，使 Agent 能在长程任务中主动或按上下文阈值压缩历史交互，保留任务进展、当前工作状态和工具经验，并基于折叠后的结构化 session state 继续推理和执行。

## 5. 30 秒面试讲法

Bear Code 是我用 Python 实现的一个自进化命令行 Coding Agent。它的核心是自研 Agentic Harness，不是简单套 API，而是统一编排模型推理、工具调用、权限控制、自主会话记忆折叠、Skills、MCP 和子 Agent。最大亮点有两个：一是会话记忆可以在长对话中主动折叠，把上下文压成结构化 session state，适合长程任务；二是 Skills 自进化与评测，系统会把用户下一轮反馈作为证据沉淀成 `SKILL.md`，再用真实 replay、规则编译、LLM judge、candidate variants 和 champion 机制评估 Skill 是否稳定可用。

## 6. 1 分钟面试讲法

这个项目主要解决两个问题：第一，怎么把大模型变成能安全执行软件工程任务的本地 Agent；第二，怎么让 Agent 在使用过程中沉淀能力。  

我实现了一个 Python Agentic Harness，负责模型调用、tool call 解析、权限检查、工具执行、结果回写、会话记忆折叠和会话保存。上层支持文件读写、代码搜索、Shell、Plan Mode、OpenAI / Anthropic 双协议、Memory、Skills、MCP 和子 Agent。会话变长、工具反复失败或需要调整策略时，模型可以主动调用 `compact_context`，系统也提供上下文阈值兜底；折叠后保留任务进度、当前目标和工具经验，继续完成长程任务。

项目最核心的亮点是自进化 Skills 和在线评测。每轮回复结束后系统会保存 pending window，下一轮用户反馈会被合并为证据，再由 Extractor 抽取可复用候选，Maintainer 判断 add / merge / discard，最后写入或演化 `SKILL.md`。评测阶段会从 provenance 构造 replay，编译规则，调用 LLM judge，结合 usage stats 给出状态；如果历史回复失败，还会生成 candidate variants 重新试跑并记录 champion 产物。整个过程有权限控制、provenance 记录、版本快照和评测产物，不是无约束让模型随便改 prompt。

## 7. 2 分钟深度讲法

Bear Code 的底层是一个自研 Agentic Harness。用户输入进入 `Agent.chat()` 后，系统会初始化 MCP、检索相关 Skills、预取 Memory，然后根据配置选择 OpenAI-compatible 或 Anthropic-compatible 模型接口。模型如果返回 tool call，Harness 会先进入统一的权限检查逻辑，再分发到内置工具、Skill、MCP 工具或子 Agent，执行结果会作为 tool result 回写给模型，形成推理、行动、观察、继续推理的闭环。

在这个闭环里，我重点补了自主会话记忆折叠：当上下文变长时，模型可以主动调用 `compact_context`，系统也会在达到阈值时自动折叠，把原始对话压缩成结构化 session state 后继续执行。这样做的价值是，长任务不会因为窗口膨胀而中断，模型还能保留任务进度、工具经验和下一步动作。

我在这个闭环上做了几个扩展：第一是 Plan Mode，复杂任务先只读分析和写计划，审批后再执行；第二是 Memory 和 Skills 分层，Memory 记录事实和偏好，Skills 记录可复用方法；第三是 MCP Client，通过 stdio JSON-RPC 动态接入外部工具；第四是子 Agent，用隔离上下文处理探索、规划和局部任务。

最重要的是 Skills 治理。系统会把用户任务、助手回复和下一轮用户反馈组成 pending window，用 Extractor 抽取未来可复用的规则，再由 Maintainer 做 add / merge / discard。在线 add/merge **只写入 Candidate**，不会改 Active。随后 `/skill-eval` 在同一次运行里重新生成 no_skill / current_champion / candidate 三臂，Gate 检查 NTR、成对收益、成本增幅、硬失败和 Holdout；通过后仍需 `/skill-promote` 原子激活。事件级 Trace 把每次对话和 REPL 治理命令收成独立 run，`benchmarks/` 用冻结配置复跑。

## 8. STAR 表达

### S：背景

普通大模型工具完成任务后，经验只停留在当前上下文中；用户下次提出同类任务时仍需要重复说明偏好、格式和工作流。同时，让模型直接操作文件和 Shell 存在安全风险；如果把用户反馈直接写进线上 Skill，一次噪声就会污染能力库。

### T：目标

实现一个本地 Harness Agent，不仅能安全执行软件工程任务，还能从用户反馈中沉淀可评测、可回滚的 Skills，并用可复现 Benchmark 证明运行时行为。

### A：行动

- 设计 Agentic Harness：RuntimeConfig 共享预算，PolicyEngine 做硬边界，ToolCallScheduler 按模型顺序切段。
- 设计自主会话记忆折叠机制，在上下文膨胀、重复失败或策略切换时压缩历史交互，保留关键任务状态并支持折叠后继续执行。
- 实现文件读写、精确编辑、代码搜索、Shell、Plan Mode 状态机、MCP 信任、子 Agent 和 Skills 调用。
- 设计 Skills 自进化链路：pending window + Extractor / Maintainer；在线落点是 Candidate。
- 实现六态治理：Candidate → Shadow → Gate → Champion → Active → Rollback；激活前快照，POSIX `os.replace` 原子写。
- 实现三臂成对评测和 NTR Gate，禁止用历史 assistant 回复当 Champion 基线。
- 补齐事件级 Trace 与 `benchmarks/`：未知成本为 null，REPL 命令独立 run，CI 无真实 Key。

### R：结果

项目形成了一个可运行的自进化 Harness Agent：既能完成代码阅读、文件编辑、测试执行、架构分析等 Coding Agent 任务，又能通过自主会话记忆折叠稳定推进长程任务。用户反馈改不到线上 Active；Skill 晋升可审计、可回滚；评测结果来自 `runs/<run_id>/`，不依赖未验证的外部分数。

## 9. 面试高频问题和回答

### Q1：为什么说它是 Harness Agent，而不是普通聊天机器人？

普通聊天机器人主要是用户输入、模型回复。Bear Code 的核心是 Harness：模型只提出 tool call，真正的文件读写、Shell、Skill、MCP 和子 Agent 都由 Runtime 统一做权限检查、执行调度、结果回写和状态保存。也就是说，它有完整的推理、行动、观察、继续推理闭环。

### Q2：自进化 Skills 到底怎么实现？

每轮回复结束后保存 pending window。下一轮用户输入会作为上一轮反馈证据合并进去，然后进入 `online_ingest()`：Extractor 从对话窗口抽取最多一个可复用候选 Skill；Maintainer 结合已有 Skills 做相似检索，判断 add、merge 或 discard。add / merge 调用 `create_candidate()`，写入 `.bear/skill-evolution/candidates/`，**不改 Active**。之后必须 `/skill-eval` 过 Gate，再 `/skill-promote` 原子激活。`/skill-create` 与 `/skill-evolve` 是手工写 Active，不属于这条自动链路。

### Q2.1：Skills 评测怎么做？

`/skill-eval` 读取 Candidate / Champion，构造 replay + holdout（生成样本强制降为 replay）。同一次运行重新生成三臂：`no_skill`、`current_champion`、`candidate`，禁止拿历史 `latest_assistant` 当 Champion 基线。规则由 `skill_rules.py` 编译，三臂共用。Gate 看硬失败、成对收益、NTR、成本增幅、Holdout；Judge 与 Generator 同模型只能 `incubating`。通过后 `mark_champion`，Active 仍需 `/skill-promote`。命令本身走 `_traced_operation`，有独立 Trace run。

### Q3：怎么避免沉淀垃圾 Skill？

有四层控制。第一，Extractor 只抽取用户明确给出的、未来同类任务可复用的规则。第二，Maintainer 优先 merge 或 discard，避免重复膨胀。第三，在线落点是 Candidate 目录，物理上改不到 Active。第四，Gate 要求成对收益、NTR、成本、硬失败和 Holdout；不满足则 incubating，不会自动晋升。

candidate 只写入评测产物和 Candidate 目录，不会自动覆盖 active `SKILL.md`。手工 `/skill-create` 是用户显式命令，另算一条路径。

### Q4：Memory 和 Skills 的区别是什么？

Memory 主要承载会话状态、任务进度和可折叠的上下文，例如当前做到哪一步、哪些工具试过、下一步怎么接；Skills 记方法和流程，例如代码审查要先列风险、政府报告要使用正式语体和固定结构。简单说，Memory 解决“长任务怎么不断档”，Skills 解决“同类任务怎么复用方法”。

### Q5：怎么保证 Agent 不乱改文件？

首先有 Plan Mode 状态机：DEFAULT → PLANNING → AWAITING_APPROVAL → EXECUTING，审批 await 计划正文，规划阶段硬阻断写和 Shell。其次 `PolicyEngine` 按路径边界 → deny 规则 → Plan Mode → MCP 信任 → allow → bypass → 确认矩阵判定；项目 allow 规则不能抬升 Plan / MCP 硬边界。再次，子 Agent / Skill fork 权限只能降不能升。编辑已有文件前必须先 `read_file`，并记录 mtime。MCP 信任写在 `~/.bear/mcp-trust/`，不进仓库。

### Q6：MCP 在项目里起什么作用？

MCP 用来把外部工具接入 Agent。Bear Code 自己实现了 stdio JSON-RPC MCP Client。仓库级 `.mcp.json` / `.bear/settings.json` 必须先被用户信任才会启动 Server，信任哈希记在用户目录 `~/.bear/mcp-trust/<workspace_id>.json`，避免克隆后预信任。

### Q7：为什么要支持子 Agent？

子 Agent 用来隔离上下文和任务范围。比如 explore 只读搜索代码，plan 只读输出方案，general 可以处理局部任务。这样主 Agent 不需要承载所有搜索细节，复杂任务也能拆分成更小的独立上下文。

### Q8：项目最大的技术难点是什么？

难点不是调用模型 API，而是把模型、工具、策略、预算、上下文、长期记忆和自进化沉淀串成稳定闭环。自进化既要能自动沉淀用户反馈，又不能让模型无约束修改自己的能力，所以需要 Candidate 目录隔离、三臂重跑、Gate、原子 promote 和 Trace 可追溯。评测侧还要处理未知 token 成本，不能把缺失 usage 记成 0。
