### **请你介绍一下 Bear Agent 这个项目。**

Bear Agent 是我用 Python 从零实现的一个本地命令行  Agent Runtime。它的核心不是简单调用一次大模型 API，而是实现了一套 Agentic Harness，也就是由 Runtime 统一编排模型推理、工具调用、权限控制、上下文压缩、会话恢复、长期记忆、Skills、MCP 外部工具和子 Agent。

整个系统的工作方式是：模型只负责推理和提出 tool call 意图，真正的文件读写、Shell 执行、Skill 调用、MCP 工具调用都由 Harness 做权限检查、执行调度和结果回写。这样可以把大模型变成一个可控的本地 Coding Agent，而不是让模型直接操作环境。

项目里我最重点做的是 Skills 自进化。系统会把上一轮任务、助手回复和下一轮用户反馈组成 pending window，然后从用户反馈中抽取可复用规则，再经过 add、merge、discard 决策，最终沉淀为项目级或用户级的 `SKILL.md`。同时它会记录 provenance、版本快照和 usage stats，保证这个自进化过程可追踪、可审计。

如果用一句话总结，这个项目是一个集成工具调用、权限控制、长期上下文和能力沉淀的自进化 Harness Agent。

### **项目里哪些地方体现了 Harness Agent 的设计？**

主要体现在三点：

第一，模型不直接执行动作，只返回 tool call。动作由 Harness 做权限检查和实际执行。

第二，工具结果不是简单打印，而是作为 tool result 回写给模型，让模型基于真实环境反馈继续推理。

第三，任务结束后 Harness 继续负责状态管理，包括 session 保存、上下文压缩、Skill usage tracking 和在线自进化。这说明项目的核心是 Runtime，而不是一次性模型调用。

### **模型循环为什么不是只调用一次模型？**

Agent 的任务通常需要多轮“观察环境”。模型第一次可能只知道要读文件，读完后才能决定怎么改；改完后还可能要运行测试。一次模型调用无法完成这种多步任务。

所以 Bear Code 的模型循环是：模型返回文本或工具调用；如果有工具调用，Runtime 执行工具并把结果回写；模型基于结果继续推理。直到模型不再调用工具，本轮对话才结束。

### **Skills 和 Memory 有什么区别？**

Memory 记事实和偏好，Skills 记方法和流程。

比如“这个项目部署在某台机器上”是 Memory；“以后写部署文档都按背景、步骤、验证、回滚风险组织”是 Skill。

简单说，Memory 解决“知道什么”，Skills 解决“怎么做”。







### **自进化 Skills 是怎么实现的**

当前轮任务结束后，系统不会马上把经验写成 Skill。它会先保存一个“待观察窗口”，里面记录这轮用户的问题、助手的回答，以及当时命中的相关 Skills。

等用户下一轮继续输入时，系统会把这句话当作对上一轮结果的反馈。比如用户说“以后都按这个格式来”“刚才那种写法不要再用”，这类反馈就会和上一轮记录合并起来，作为是否沉淀 Skill 的依据。

之后系统会判断这条反馈里有没有未来可复用的方法或规则。如果有，就整理成一个 Skill 候选，再和已有 Skills 做比较：如果是一个新的能力，就创建新的 `SKILL.md`；如果和已有 Skill 很接近，就合并到已有 Skill 里；如果只是一次性内容、价值不高或者证据不够，就不会写文件，只记录这次判断过程，方便后面追踪。

这样设计的好处是：系统不会凭助手自己的猜测随便改能力库，而是等用户明确反馈后再沉淀，减少错误 Skill 和重复 Skill。

### **为什么要把“找经验”和“写 Skill”拆开？**

拆开是为了降低“抽取即写入”的风险。

第一步只判断“这段对话里有没有可复用经验”，如果有，就整理成一个候选 Skill，但不会直接写文件。

第二步再判断“这个候选应该怎么放进现有 Skills 体系里”。如果已有 Skill 能承载，就合并进去；如果确实是新的能力，就新建；如果证据不足或价值不高，就放弃写入。

这样做可以避免系统一发现一句反馈就马上写文件，也能减少重复 Skill 和低质量 Skill。

### **怎么避免沉淀垃圾 Skill？**

有几层控制。

第一，只沉淀用户明确表达的、未来同类任务仍适用的方法或偏好，不沉淀一次性任务内容、密钥、账号、URL、精确日期和临时项目事实。

第二，新候选会先和已有 Skills 做比较。如果已有 Skill 已经能覆盖这条经验，就优先合并，而不是随便新建。

第三，每次判断都会记录来源和结果。即使最后没有写 Skill，也能追踪当时为什么放弃。

第四，usage tracking 会统计 retrieved、relevant、used。如果某个 Skill 长期被检索但没有实际使用，就可能被归档。

### **为什么要用下一轮用户反馈，而不是当前轮结束就沉淀？**

因为当前轮结束时，Agent 不知道用户是否认可它的输出。如果立刻沉淀，容易把一次性任务内容、临时项目事实或 assistant 自己总结出的规则写成长期 Skill。

下一轮用户反馈通常更可靠，比如“以后都按这个格式来”“刚才那种写法不要再用了”“这类任务要先给结论”。这些是明确的稳定偏好，更适合作为 Skill 沉淀证据。







### **项目最大的技术难点是什么**

最大难点不是调用模型 API，而是把模型、工具、权限、上下文、长期记忆、自进化和评测串成稳定闭环。

具体难点有三类：

第一是执行安全。模型可以调用文件和 Shell，但所有副作用必须被 Runtime 控制。

第二是长期上下文。Memory 和 Skills 要分工清楚，否则事实、偏好、方法会混在一起。

第三是自进化治理。自动沉淀 Skill 很容易污染能力库，所以必须先保存待观察窗口，再用用户下一轮反馈作为证据，并记录来源、使用效果和评测结果。

### **为什么不用 LangChain / AutoGen 这类框架？**

这个项目的目标是学习和实现 Coding Agent 底层机制，而不是快速拼应用。如果使用重型框架，很多关键细节会被封装掉，比如工具结果回写、权限判断、编辑前读取保护、Anthropic/OpenAI 工具调用差异、待观察窗口和 Skill 评测产物。

我选择自己实现 Harness，是为了把 Agent Runtime 的关键链路都掌握在项目里。这样更利于面试展示，也方便后续按自己的需求扩展。

### **如果让你继续优化，你会做什么？**

我会优先做四件事。

第一，抽象模型适配层，把 OpenAI / Anthropic 的消息格式和工具格式适配进一步模块化。

第二，增强 Skills 检索，引入可选向量检索或 hybrid search，但保持 BM25\-lite 作为无依赖 fallback。

第三，完善在线评测到当前 Skill 的升级流程。当前健康版本记录只是评测产物，不自动覆盖当前 Skill，后续可以加人工审批后的升级流程。

第四，补更多测试，尤其是权限模式、Plan Mode、Skill 新建/合并/放弃写入、MCP 工具路由和在线评测门控。

### **你觉得这个项目最能体现你能力的地方是什么？**

我觉得最能体现能力的是系统设计和工程边界。这个项目不是堆功能，而是围绕 Agentic Harness 建了一套闭环：模型协议适配、工具调用、权限控制、上下文管理、长期记忆、Skills、自进化、MCP、子 Agent 和在线评测都在一个 Runtime 里协作。

尤其是 Skills 自进化部分，我没有让模型直接改 prompt，而是先保存待观察窗口，等下一轮用户反馈进来后再判断是否沉淀，并且记录来源、版本、使用效果和在线评测结果。这样“自动沉淀能力”不是黑箱行为，而是一个可治理的流程。这比单纯做一个能聊天或能改文件的 Agent 更有工程挑战。
